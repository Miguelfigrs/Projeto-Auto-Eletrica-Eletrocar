CONTEXTO

Por que este sistema existe

› Problema: Lentidão nas filas de balcão, perda de foco ao bipar peças, dificuldade do eletricista digitar na oficina com luvas/graxa, perda de receita e divergências de estoque/caixa.
› Restrição: Tempo de resposta < 150ms no PDV; operação 100% por atalhos de teclado; alta tolerância a falhas offline.
› Abordagem: PWA React + FastAPI assíncrono + PostgreSQL 16 + Hardware I/O (WebHID/Serial) + Telegram Voice Bot com Whisper ASR.
› Método: UML + DDD + Clean Architecture + TDD (Engenharia de Software de Alta Resiliência).

Decisão Arquitetural Resumo Executivo e Justificativa de Negócio
RBAC com Acúmulo de Papéis Suporta Dono da Oficina atuando como Administrador, Balconista e Mecânico simultaneamente via tabela associativa N:N.
Captura Global de Barcode Diferenciação temporal por buffer (delta < 25ms) para separar leitor óptico de digitação humana — dispensa foco de cursor.
Abertura de OS por Voz (Telegram) Eletricista grava áudio na baia; Whisper ASR transcreve e LLM extrai JSON estruturado (Cliente, Carro, Sintomas) em < 5s.
Integridade ACID & Fechamento Cego Transações atômicas com bloqueio otimista de estoque e fechamento de caixa cego para auditoria sem quebra de valores.

SEÇÃO 02 · CASOS DE USO

Casos de Uso Principais — Descrição Textual

UC02: Realizar Venda no Balcão
› Ator Principal: Balconista (ou Dono Multi-Perfil).
› Pré-condições: Caixa do dia aberto e usuário autenticado.
› Fluxo Principal:
1. Balconista pressiona F2 para nova venda.
2. Aponta o leitor óptico nas peças (UC03); sistema emite bip e adiciona itens (< 150ms).
3. Balconista tecla F9 para tela de pagamento.
4. Escolhe PIX (QR Code dinâmico gerado), Cartão ou Dinheiro.
5. Confirma recebimento; backend processa transação ACID, baixa estoque e gera recibo térmico.
› Pós-condições: Estoque deduzido e caixa atualizado.
UC06: Enviar Áudio Telegram / IA
› Ator Principal: Eletricista / Mecânico.
› Pré-condições: Telegram User ID autorizado na whitelist do banco.
› Fluxo Principal:
1. Eletricista envia áudio no bot do Telegram relatando sintomas e peças.
2. Webhook aciona Whisper ASR para transcrição.
3. LLM extrai JSON estruturado com terminologia automotiva.
4. Backend vincula cliente e veículo e gera a OS em status inicial.
5. WebSocket emite alerta no balcão e bot retorna confirmação com botões inline.
› Pós-condições: OS salva no banco de dados e visível no pátio.

SEÇÃO 03.1 · BANCO DE DADOS

Integridade Referencial e Transações ACID

🔒 Prevenção de Estoque Negativo

Uso de bloqueio pessimista temporário na finalização de vendas:
SELECT estoque_atual FROM pecas WHERE id = :id FOR UPDATE;
Garante que vendas simultâneas no balcão e na oficina não ultrapassem o saldo físico.

🛡️ Soft-Delete e Auditoria Contínua

Ordens de serviço, clientes e produtos utilizam a coluna deleted_at (timestamptz). Registros fiscais e contábeis jamais são destruídos via DELETE rígido.

⚙️ Transações Atômicas de Caixa

Se a emissão do comprovante ou o registro contábil falharem, a transação realiza ROLLBACK integral, restaurando o estoque e cancelando o débito no caixa.

📜 Triggers de Histórico Automático

Toda alteração em preços de peças gera automaticamente uma linha na tabela de auditoria com o usuário logado e a variação de valor.

SEÇÃO 05 · DIAGRAMA DE ESTADOS

Ciclo de Sincronização Local × Remoto

🔄 Máquina de Estados da Sincronização PWA

1. PENDENTE: Venda ou rascunho de OS registrado localmente no IndexedDB.
2. ENFILEIRADO: Registro adicionado à SyncQueue do cliente.
3. SINCRONIZANDO: Service Worker detecta rede online e transmite lote via HTTPS.
4. SINCRONIZADO: Servidor responde HTTP 200/201; item é removido da fila local.
5. ERRO / RETRY: Falha de conexão; aplica backoff exponencial (1s, 2s, 4s, 8s).

⚡ Resolução de Conflitos

• Regra Last-Write-Wins: Conflitos em cadastros são resolvidos com base na data updated_at mais recente.
• Transações Financeiras: Sempre verificadas no servidor antes de confirmar liquidação final.
• Indicador Visual: Ícone no cabeçalho exibe [🟢 Sincronizado], [🟡 Sincronizando...] ou [🔴 3 Pendentes].

Clean Architecture — Estrutura de Camadas e Pastas

src/

  ├── domain/              # Entidades puras, Value Objects, Domain Services, Interfaces Repositório

  │   ├── entities/        # Usuario, OrdemServico, Peca, VendaBalcao, Cliente

  │   ├── value_objects/   # PlacaVeiculo, CodigoBarras, Dinheiro

  │   └── repositories/    # IOrdemServicoRepository, IPecaRepository (Interfaces puras)

  ├── application/         # Casos de uso (Use Cases) e orquestração de negócios

  │   ├── use_cases/       # RealizarVendaUseCase, CriarOSVozUseCase, EmitirDREUseCase

  │   └── dtos/            # Modelos de entrada/saída Pydantic v2

  ├── adapters/            # Controladores, Presenters e Gateways concretos

  │   ├── controllers/     # Rotas FastAPI REST e Handlers WebSockets

  │   ├── gateways/        # BarcodeGateway, TelegramWebhook, WhisperAdapter

  │   └── repositories/    # Implementações SQLAlchemy 2.0

  └── infra/               # Configurações externas, banco e drivers

      ├── db/              # PostgreSQL 16 engine, migrations Alembic

      └── hardware/        # WebHID e Web Serial device listeners

⚠️ Regra Estrita de Verificação: domain/ e application/ jamais importam SQLAlchemy, FastAPI, WebHID ou bibliotecas de terceiros diretamente.
